## Approved strict checked-int32 contract

In checked mode, signed `int32` addition, subtraction, and multiplication terminate nonzero on overflow or underflow. Division and remainder terminate nonzero for a zero divisor and for `INT32_MIN / -1` or `INT32_MIN % -1`. Successful boundary operations produce their mathematical `int32` result. The C runtime uses widened `int64_t` add/subtract/multiply intermediates and explicit divide/remainder guards, so it does not evaluate an overflowing signed operation.

Coverage is **1 C codegen snapshot** proving `sn_{add,sub,mul,div,mod}_int32` helper selection; **8 C integration cases** (one successful boundary result and seven isolated nonzero failure cases); and **8 Rust rgen cases** with `.expected.rs` snapshots (one successful output and seven `.panic` cases). The seven failure cases on each target are add overflow, subtract underflow, multiply overflow, divide-by-zero, remainder-by-zero, `MIN / -1`, and `MIN % -1`.

Unchecked/debug-overflow behavior, exact cross-target diagnostic/status parity, literal parsing, unary negation, and `SN_RUSTFLAGS` semantics remain open.

## Approved strict checked-int/long contract

In checked mode, both signed `int` and `long` use the shared signed-i64 path: C lowers both spellings to `long long` and `sn_{add,sub,mul,div,mod}_long`, while Rust lowers both to `i64.checked_{add,sub,mul,div,rem}`. Addition, subtraction, and multiplication use portable C99 pre-operation `LLONG_MIN`/`LLONG_MAX` predicates and never evaluate a signed-overflowing expression. Division and remainder first reject a zero divisor, then reject `LLONG_MIN / -1` and `LLONG_MIN % -1` before evaluating the operator. Overflow diagnostics are `Runtime error: integer overflow in addition/subtraction/multiplication/division/modulo`; zero diagnostics remain `panic: Division by zero` and `panic: Modulo by zero`; each path exits 1.

Coverage is **1 C codegen snapshot** proving both spellings emit `long long` and all five shared helpers; **8 C integration cases** and **8 Rust rgen cases**. The combined boundary case covers both spellings and all five operations. The isolated failures retain `int` add overflow and subtract underflow, and add `long` multiply overflow, division-by-zero, remainder-by-zero, constructed `MIN / -1`, and constructed `MIN % -1`. Default-optimization sidecars cover the existing `int` add-overflow and new `long MIN / -1` division cases on both targets.

Unchecked/debug-overflow behavior, exact cross-target diagnostic/status parity, literal parsing, unary negation, and `SN_RUSTFLAGS` semantics remain open.

## Approved strict checked scalar `as ref` parameter-mutation contract

In checked mode, a direct variable place backed by an `int as ref`, `long as ref`, `int32 as ref`, `byte as ref`, `uint32 as ref`, or `uint as ref` parameter uses the same checked helpers as a local: add, subtract, multiply, divide, remainder, and postfix increment/decrement. The C model admits exactly that narrow category through `mutation_is_checked_scalar_ref_parameter` in `src/cgen/gen_model_expr.c`; it still requires a direct, non-captured `MEM_AS_REF` parameter variable and excludes sync, nested/computed, index, and by-value places. C emits `sn_{add,sub,mul,div,mod}_long`, `sn_{add,sub,mul,div,mod}_int32`, `sn_{add,sub,mul,div,mod}_byte` against `unsigned char *`, `sn_{add,sub,mul,div,mod}_uint32` against `uint32_t *`, or `sn_{add,sub,mul,div,mod}_uint` against `uint64_t *`, evaluating a compound RHS once before taking the parameter place (`templates/c/partials/expr/compound_assign.hbs`). Rust validates the same model category via `rust_checked_scalar_ref_parameter`, accepts `uint32` and `uint` parameters in free-function/static/plain-instance validation, marks scalar-ref uses in both function and struct-method bodies with `rust_lower_scalar_ref_parameters`, and renders them as stable `&mut u32` and `&mut u64` places using `checked_{add,sub,mul,div,rem}` in `templates/rust/partials/expr/{compound_assign,increment,decrement}.hbs`.

The shared call-model path now reads a resolved instance method's parameter qualifiers before rendering its arguments (`EXPR_CALL` lowering in `src/cgen/gen_model_expr.c`). The type checker preserves method parameter qualifiers in each synthesized function type through `copy_method_param_mem_quals` in `src/type_checker/expr/type_checker_expr_member.c`, then applies `validate_as_ref_argument_place` in `src/type_checker/expr/call/type_checker_expr_call_core.c` to free, static, and plain-instance calls. The validator handles parsed field chains through `EXPR_MEMBER` and the distinct `EXPR_MEMBER_ACCESS` union arm, requiring their receiver chain to end in a variable; it rejects method-valued members, indexes, literals, computed expressions, and fields of temporary values before either backend can emit an address or mutable temporary. Forwarding an existing `as ref` parameter remains a valid single reference/borrow. This does not enable instance `as ref` struct receivers; the established variable-or-field rule continues to exclude array/index places.

PR #78 adds **one C snapshot**, **one model snapshot**, **eight C integration cases**, and **eight Rust rgen behavior cases**: `checked_ref_parameter_uint_mutations` covers free/static/plain-instance uint forms, all five same-type compound operators, postfix prior-value semantics, caller-visible mutation, RHS-once ordering (`value += oldThenIncrement(value)`), direct reads, forwarding, direct/nested variable-rooted fields, a high-bit assignment/read across the reference ABI, and separate successful zero/max boundaries. Its seven isolated failure cases per backend are add overflow, subtract underflow, multiply overflow (computed high bit times `2u`), divide-by-zero, remainder-by-zero, postfix increment overflow, and postfix decrement underflow; all Sindarin operands use the `u` suffix. The positive fixture constructs `half`, `high`, `max_minus_one`, and `max` without literals above `INT64_MAX`, and reports high-bit/max behavior only through boolean equality. Existing signed/byte/uint32 scalar-ref fixtures and call-place negatives retain their coverage and exclusions. `captured_ref_parameter_mutation` still proves that `mutation_base_is_captured` preserves C's unchecked capture behavior. Sindarin has postfix-only `++`/`--`; prefix forms are not a language feature.

The checked-integer slice deliberately excludes by-value parameter mutation (including the pinned `by_value_parameter_compound_mutation` diagnostic), capture lowering, heap-owning and instance-reference work, sync, nested/computed/index/temporary mutation places, floating mutation from the checked-helper path, and unrelated PR-D scope. No checked scalar-integer `as ref` rejection remains. C captured scalar-ref parameters preserve their established unchecked path; Rust lambdas remain separately unsupported. Unchecked integer parameter behavior remains its established raw-operation policy.

## Approved floating scalar `as ref` parameter contract

Rust accepts direct `float as ref` and `double as ref` parameters on free functions, static methods, and plain instance methods. Signatures use `&mut f32` and `&mut f64`; `rust_lower_scalar_ref_parameters` marks callee reads and direct assignments for dereference, so assignments update caller storage. Calls reuse the shared `validate_as_ref_argument_place` contract: only established variable places and fields whose receiver chain ends at a variable are accepted, while forwarding an existing `as ref` parameter emits a single reborrow. Literals, computed expressions, temporary-rooted fields, indexes/array elements, captures, sync, heap-owning parameter forms, and instance-reference receivers remain excluded.

Floating-reference mutation remains outside checked scalar mutation: `rust_checked_scalar_ref_parameter` is still integer-only. The target-local `rust_floating_ref_parameter` predicate admits only a direct variable mutation whose storage is a parameter, whose parameter qualifier is exactly `as_ref`, and whose resolved type is exactly `float` or `double`. That category joins existing stable floating locals for same-type `+=`, `-=`, `*=`, `/=`, and postfix `++`/`--`; it does not widen direct fields or any other place/storage family. Existing floating lowering evaluates a compound RHS once before forming the place once, stores and returns the new value, and makes postfix copy and return the prior value before storing prior plus or minus floating `1.0`.

`floating_ref_parameter_mutations` supplies matching model, C, and Rust snapshots plus explicit-C, default-C, and Rust behavior. It covers the full two-type, six-operator, three-context matrix; expression-return semantics; caller-visible storage; forwarded references in every context; direct variable, direct-field, and nested variable-rooted-field call sites; and collisions with `__sn_rhs`, `__sn_place`, `__sn_next`, and `__sn_previous`. Every compound RHS calls a static helper that mutates only an independent integer counter, proving one evaluation without aliasing the floating target. The Rust snapshot pins the single target rendering. The earlier direct read/write fixture remains unchanged.

`%=` and mixed float/double or floating/integer operands remain rejected, as do by-value parameters, captures, sync/global storage, nested/computed/indexed/array/temporary mutation places, owning/reference families, instance `as ref` receivers, `char as ref`, and prefix forms. The two obsolete blanket floating-reference mutation negatives are replaced by `floating_as_ref_parameter_modulo_mutation` and `floating_as_ref_parameter_mixed_type_mutation`, which pin the operator and exact-type diagnostics. Neighboring general-place, by-value, sync, closure, global, ownership, receiver, character, and parser diagnostics retain their established precedence.

## Approved bounded floating compound-mutation contract

Rust accepts exactly same-type `float`/`float` and `double`/`double` `+=`, `-=`, `*=`, and `/=` on an existing stable mutable local variable, a normal-array foreach-local binding, or a one-level direct field whose receiver is an established local or `self`. The expression evaluates its RHS once, then forms the target place once, performs ordinary Rust `f32`/`f64` arithmetic, stores the result, and returns that newly stored value. Division therefore has ordinary IEEE-754 Rust behavior, including infinity rather than an integer-style checked failure for a zero divisor. Floating mutations never use `checked_*` integer helpers.

The implementation is target-local and reuses the existing shared `mutation_op`, `mutation_place`, `mutation_storage`, `mutation_sync`, and resolved type annotations; it does not change the AST or shared model. `rust_lower_floating_mutations` only marks an already-validated floating compound expression for raw Rust lowering. `tests/rgen/floating_compound_mutations.*` supplies one emit/snapshot/build/run case with nine boolean output lines covering both types and all four operators, expression result values, local/direct-local-field/direct-`self`-field places, mutable cloned foreach bindings with unchanged source arrays, zero-divisor behavior, and an RHS that increments only a separate counter to prove one evaluation without adding an aliasing or operand-order contract. User variables named `__sn_rhs`, `__sn_place`, and `__sn_next` are themselves compound targets, directly pinning lexical helper collision safety.

Floating `%=` remains rejected, as do mixed float/double and floating/integer operands in either target/RHS direction, by-value parameters, captures, sync storage, nested fields, array/index places, and every computed or temporary-rooted place. The original floating-compound negatives continue to pin that general boundary; the floating-reference completion adds precise parameter `%=` and mixed-type cases instead of a blanket reference rejection. The capture source is deliberately expected to report `Error: Rust target does not support closures yet`: capture is modelable, but whole-model closure validation precedes expression mutation-place validation, so no capture-specific floating diagnostic is reachable without changing production validation order.

## Approved normal-array foreach checked-mutation contract

A normal-array foreach binding is an independently owned mutable local snapshot, not a parameter or a reference to the source element. The type checker records it as `SYMBOL_FOREACH_LOCAL`, which allocates through the local-offset path and makes resolved variable expressions non-parameter places. The distinct symbol kind avoids broadening real parameter semantics. The C foreach model/template remains responsible for acquiring and cleaning up string, nested-array, function, value-struct, and reference-struct bindings; returning a foreach binding now follows local escape marking, consistent with the existing owned-return transfer path. Lambda model capture analysis already registers foreach names as locals, so the classification does not turn a loop binding into an outer capture. Iterator-protocol foreach bindings retain their pre-existing `SYMBOL_PARAM` classification; the Rust-only scope marker described below does not change shared type checking or normal-array lowering.

Coverage is **1 model snapshot**, **1 C snapshot/build/run case**, and **3 Rust snapshot/build/run cases**. `foreach_checked_mutations` covers `+=`, `/=`, postfix `++`/`--`, compound and postfix result values, two RHS calls proving one evaluation apiece, and an unchanged source slot. ## Approved iterator-protocol scalar contract

The source-language protocol remains the existing C contract. A non-array iterable struct must define a zero-explicit-parameter instance `iter()` returning a struct. That iterator struct must define zero-explicit-parameter instance `hasNext(): bool` and `next(): T`, where `T` is non-`void`. The iterable expression is evaluated exactly once to initialize a distinct mutable iterator value. Each condition check calls `hasNext()` once; only a true result is followed by one `next()` call. The returned value initializes a fresh mutable loop binding, so assigning the binding does not alias either the source or the iterator. The first false `hasNext()` terminates natural iteration; `break` and `continue` retain ordinary loop behavior. Mutating iterator receivers are part of the existing contract: both C and Rust pass a mutable iterator receiver to state-changing `hasNext()` and `next()` methods.

Rust admits only plain heap-free value iterable and iterator structs (`mem_mode == val`, non-ref receivers, and existing model cleanup kind `none`) whose `next()` element is one of `int`, `long`, `int32`, `uint`, `uint32`, `byte`, `double`, `float`, `bool`, or `char`, also with cleanup kind `none`. Before rendering, Rust annotates each iterator statement with a generated local name that is absent from every string in the complete model; names already assigned to inner/adjacent iterator statements participate in the same check. The Rust partial uses that model-supplied name for the block-scoped mutable iterator, emits `while iterator.hasNext()`, and creates a fresh mutable element from `iterator.next()`. This preserves legal user locals and loop bindings and keeps nested iterator temporaries distinct. Iterator foreach is also a nested-loop boundary for the existing C-style-for `continue` rewrite.

`iterator_protocol_scalar` supplies **1 shared model snapshot**, **1 C snapshot/build/run case**, **1 default-C integration case**, and **1 Rust snapshot/build/run case**. ## Approved Rust scalar and managed-handle `sizeof` contract

Rust accepts `sizeof` only when the resolved operand type is `int`, `long`, `int32`, `uint`, `uint32`, `byte`, `bool`, `char`, `float`, `double`, `str`, or a normal array. It emits an explicit `i64` literal using the Sindarin/C sizes: 8 bytes for `int`/`long`/`uint`/`double` and for `str`/normal-array managed handles, 4 for `int32`/`uint32`/`float`, and 1 for `byte`/`bool`/`char`. It does not use Rust `size_of` or native layout; in particular, source `char` remains one byte even though Rust `char` has a different native representation.

Both existing parenthesized and bare type/expression spellings are supported. Expression operands are type-checked by the shared front end, but Rust validation and rendering consume only the model's resolved `target_type`; the modeled operand subtree is never rendered, evaluated, or used to acquire ownership. `sizeof_fixed_scalars` proves all ten scalar type spellings, variable and call operands, optional parentheses, arithmetic/comparison composition, and a side-effecting scalar call whose counter remains zero. `sizeof_managed_handles` adds `str`, scalar/nested/struct-element normal-array type and expression forms, string/array variables, and side-effecting string/array-returning calls whose counter remains zero. Structs, pointers, functions, `void`, `nil`, opaque/interface names, generics without a resolved supported specialization, and every other excluded kind remain rejected. Struct/pointer/function/void/nil/interface target diagnostics are dedicated Rust boundaries. An opaque declaration retains the existing earlier Rust top-level-type-declaration rejection before its `sizeof` expression is visited; this slice does not broaden validation ordering merely to classify it differently. The existing missing-parenthesis fixture likewise remains a shared parse boundary. C acceptance and C's `sizeof(type)` emission are unchanged.

## Approved normal-array foreach string compound-assignment contract

A normal-array `str` foreach binding is a mutable owned copy of its source element. C keeps the established duplicated loop-local pointer, frees the old local value after concatenation, cleans up a heap-producing RHS once, and leaves the array slot valid and unchanged. Rust keeps `for mut ... in ...iter().cloned()`. Its string-compound expression evaluates the RHS first, then forms one mutable reference to the target, appends through that stable place, and clones the updated value through the same place. Consuming that result therefore creates an independent owner on both targets; dropping the result or loop binding cannot invalidate the other or the source array. The RHS and target are each evaluated exactly once per operation.

Coverage is **1 model snapshot**, **1 C snapshot/build/run case**, **1 Rust snapshot/build/run case**, and **1 default-C integration case**. `foreach_string_compound_assignment` consumes each compound result across three iterations, checks the mutated binding and original source element side by side, and proves exactly three RHS calls. ## Approved strict checked-uint contract

In checked mode, source-language `uint` addition, subtraction, and multiplication terminate nonzero when their mathematical result is outside `0..UINT64_MAX`. Division and remainder terminate nonzero for a zero divisor. Successful boundary operations return their exact u64 result. The C runtime checks operands before evaluating each operation, using `a > UINT64_MAX - b` for addition, `a < b` for subtraction, and `b != 0 && a > UINT64_MAX / b` for multiplication; division and remainder guard a zero divisor before the operation. Rust uses `u64` `checked_add`, `checked_sub`, `checked_mul`, `checked_div`, and `checked_rem`.

Coverage is **1 C codegen snapshot** proving `sn_{add,sub,mul,div,mod}_uint` helper selection; **6 C integration cases** (one successful boundary result and five isolated nonzero failure cases); and **6 Rust rgen cases** with `.expected.rs` snapshots (one successful output and five `.panic` cases). Unchecked/debug-overflow behavior, exact cross-target diagnostic/status parity, literal parsing, unary negation, and `SN_RUSTFLAGS` semantics remain open.

## Parity status legend

- **IBT** — implemented & behavior-tested (rgen: snapshot `.expected.rs` + `rustc` build + run + stdout diff). Because every rgen case snapshots, compiles, runs, and checks output, implemented behavior is **not** downgraded to snapshot-only when a dedicated test is missing — classify as **UT** (under-tested) instead.
- **SNAP** — Rust partial/template exists but no dedicated rgen positive test.
- **UT** — under-tested (implemented; few/no dedicated negative/edge tests).
- **REJ** — explicitly rejected with a dedicated single-line diagnostic (rgen-errors pins first line).
- **SIL** — silently unsupported: construct reaches the Rust validator and falls through to the generic "unsupported construct" message.
- **ABSENT** — C supports it; Rust has neither a template nor a validator case.

**rgen behavior:** every rgen test does emit (`--emit-rust` → `.expected.rs` snapshot) → `rustc --edition=2021` build → run binary → diff stdout vs `.expected` when one exists. A `.panic` sidecar instead marks an expected runtime failure: it requires a genuine nonzero program exit, rejects timeouts and harness launch errors, and conflicts with `.exit`; it deliberately does not match Rust panic text or an exact exit code. **There is no Rust integration suite**; the C-side behavior suite has no wholesale `--target rust` equivalent. The rgen suite now covers the narrow pure-import subset, checked and string-compound normal-array foreach mutation, heap-free scalar iterator protocol including exact numeric binding mutation, scalar and managed-handle `sizeof`, signed/unsigned integer `toDouble`, direct floating/boolean scalar `as ref` parameters including bounded floating compound/postfix mutation, the coherent integral statement/value match family, and bounded exact-`float` normal-array search; C-only features such as files/dates/threads/closures and unsupported ownership categories remain rejected or unimplemented on Rust as recorded above.

**Exit-code sidecar:** each rgen test may ship an optional `<name>.exit` sidecar file containing a single decimal integer that pins the expected process exit code. When the sidecar is absent, the runner defaults to expecting exit code **0**; when present, the file must hold a valid decimal integer (empty or non-numeric sidecars fail the test). A test cannot use both `.exit` and `.panic`. `main_int_exit` uses `main_int_exit.exit` (value `7`) to pin the `std::process::exit` value emitted by a zero-argument `int` main; `main_int_fallthrough` has **no** `.exit` sidecar so the runner defaults to exit **0** — its `int` main reaches the closure's unconditional `return 0` fall-through (empty stdout).

**Argument sidecar:** each rgen test may ship an optional `<name>.args` sidecar — a **JSON array of strings** that the runner passes as the process's user `argv` (run_tests.py `.args` block). An **empty array** `[]` is valid (no extra args); an **empty file** (whitespace only), **invalid JSON**, a **non-array root**, **non-string elements**, or a **string with an embedded NUL** each fail the test distinctly. The sidecar is opened as **UTF-8**. These user args are appended after `argv[0]` (the binary path), so `args.length` in the program equals `1 + len(.args)` — this is what the `main_args_*` tests assert.

**Spark 1 evidence — `test_limitation_closure_array`:** during this audit the exploratory test `test_limitation_closure_array` (a closure capturing a local array, pushed from 3 concurrent threads) produced an ASAN `heap-buffer-overflow` **twice on Spark 1**, while the same focused baseline test passed **5/5 on Spark 2** and earlier full baselines were green. Classify it as a **nondeterministic / host-sensitive existing C concurrency/closure risk** (concurrent `SnArray` push → `sn_realloc` race), **not** a docs-branch or Rust-backend regression. Keep it in the **PR-G** (threads/closures) verification scope.

# VALIDATION / MERGE GATES

Per-PR gate sequence (manual, in order):
1. **Fresh worktree:** run `make setup` **once** at the start (toolchain check).
2. **Targeted Rust tests:** run the milestone's new rgen + rgen-errors + `--target rust` integration cases.
3. **`make test-rgen`:** full Rust generation/behavioral suite green.
4. **`make build && make test`:** C default target + full suite green (C regression obligation).
5. **Independent verification on another Spark machine** (second machine re-runs build + tests to confirm reproducibility).
6. **Laptop: inspect the actual `git diff` + GitHub check runs** before merge.
7. **Docs-only caveat:** CI may **skip** docs-only PRs via `paths-ignore`, but the **manual gates above still apply** — never skip the gates because CI skipped.
8. **Merge order:** merge **serially** in milestone order (A→H); **refresh/rebase** each PR onto the updated main before merging.

# CONCLUSION / STATUS

- **Parity is NOT achieved.** The Rust backend implements a partial subset (value structs, arrays including bounded exact-`float` normal-array search, strings, struct methods, copyOf/concat, the coherent integral statement/value match family, the bounded `typeOf` metadata envelope, checked direct scalar-integer int/long/int32/byte/uint32/uint `as ref` parameters, direct float/double/bool `as ref` reads/assignments/forwarding, and the narrow pure-import subset above); C-supported features across source language, runtime/SDK, diagnostics, and concurrency remain open.
- **No C-supported gap is N/A / accepted target exception.** Every missing family maps to exactly one milestone (PR-A … PR-H); each is **implementation work**, not a dismissed category.
- **Known unsupported paths require action:** each is either implemented to match C-equivalent behavior, or resolved by an **explicit user decision** (see Decision Register D1–D7). Implementation pauses when a choice would change the language contract.
- **C remains the default target** (`src/compiler.c:31`); Rust is opt-in and every change must keep C green.
