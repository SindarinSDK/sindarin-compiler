## Approved strict checked-int32 contract

In checked mode, signed `int32` addition, subtraction, and multiplication terminate nonzero on overflow or underflow. Division and remainder terminate nonzero for a zero divisor and for `INT32_MIN / -1` or `INT32_MIN % -1`. Successful boundary operations produce their mathematical `int32` result. The C runtime uses widened `int64_t` add/subtract/multiply intermediates and explicit divide/remainder guards, so it does not evaluate an overflowing signed operation.

Coverage is **1 C codegen snapshot** proving `sn_{add,sub,mul,div,mod}_int32` helper selection; **8 C integration cases** (one successful boundary result and seven isolated nonzero failure cases); and **8 Rust rgen cases** with `.expected.rs` snapshots (one successful output and seven `.panic` cases). The seven failure cases on each target are add overflow, subtract underflow, multiply overflow, divide-by-zero, remainder-by-zero, `MIN / -1`, and `MIN % -1`.

Unchecked/debug-overflow behavior, exact cross-target diagnostic/status parity, literal parsing, unary negation, and `SN_RUSTFLAGS` semantics remain open.

## Approved strict checked-int/long contract

In checked mode, both signed `int` and `long` use the shared signed-i64 path: C lowers both spellings to `long long` and `sn_{add,sub,mul,div,mod}_long`, while Rust lowers both to `i64.checked_{add,sub,mul,div,rem}`. Addition, subtraction, and multiplication use portable C99 pre-operation `LLONG_MIN`/`LLONG_MAX` predicates and never evaluate a signed-overflowing expression. Division and remainder first reject a zero divisor, then reject `LLONG_MIN / -1` and `LLONG_MIN % -1` before evaluating the operator. Overflow diagnostics are `Runtime error: integer overflow in addition/subtraction/multiplication/division/modulo`; zero diagnostics remain `panic: Division by zero` and `panic: Modulo by zero`; each path exits 1.

Coverage is **1 C codegen snapshot** proving both spellings emit `long long` and all five shared helpers; **8 C integration cases** and **8 Rust rgen cases**. The combined boundary case covers both spellings and all five operations. The isolated failures retain `int` add overflow and subtract underflow, and add `long` multiply overflow, division-by-zero, remainder-by-zero, constructed `MIN / -1`, and constructed `MIN % -1`. Default-optimization sidecars cover the existing `int` add-overflow and new `long MIN / -1` division cases on both targets.

Unchecked/debug-overflow behavior, exact cross-target diagnostic/status parity, literal parsing, unary negation, and `SN_RUSTFLAGS` semantics remain open.

## Approved strict checked scalar `as ref` parameter-mutation contract

In checked mode, a direct variable place backed by an `int as ref` or `long as ref` parameter uses the same signed-i64 checked helpers as a local: add, subtract, multiply, divide, remainder, and postfix increment/decrement. The C model admits exactly that narrow category through `mutation_is_checked_integer_ref_parameter` in `src/cgen/gen_model_expr.c`; C emits `sn_{add,sub,mul,div,mod}_long` and evaluates a compound RHS once before taking the parameter place (`templates/c/partials/expr/compound_assign.hbs`). Rust validates the same model category via `rust_checked_integer_ref_parameter`, marks scalar ref uses in both function and struct-method bodies with `rust_lower_integer_ref_parameters`, and renders a stable `&mut` place using `checked_{add,sub,mul,div,rem}` in `templates/rust/partials/expr/{compound_assign,increment,decrement}.hbs`.

The shared call-model path now reads a resolved instance method's parameter qualifiers before rendering its arguments (`EXPR_CALL` lowering in `src/cgen/gen_model_expr.c`). The type checker preserves method parameter qualifiers in each synthesized function type through `copy_method_param_mem_quals` in `src/type_checker/expr/type_checker_expr_member.c`, then applies `validate_as_ref_argument_place` in `src/type_checker/expr/call/type_checker_expr_call_core.c` to free, static, and plain-instance calls. An `as ref` argument must be a direct variable or a member chain rooted in one: literals, computed expressions, and fields of temporary values are rejected before either backend can emit an address or mutable temporary. Forwarding an existing `as ref` parameter remains a valid single reference/borrow. This does not enable instance `as ref` struct receivers; the established variable-or-field rule continues to exclude array/index places.

Coverage is **three C snapshots**, **two model snapshots**, **21 C integration cases**, **20 Rust rgen behavior cases**, **five Rust-target negatives**, and **three shared front-end integration-error negatives**. `checked_ref_parameter_mutations` covers free-function int, static long, and instance-method int/long parameter forms; all five compound operators; postfix prior-value semantics; caller-visible mutation; RHS-once ordering (`value += oldThenIncrement(value)`); and successful values. `as_ref_method_parameter_forwarding` proves free/static/plain-instance forwarding preserves the caller place without double borrowing. The literal, computed, and temporary-field static/instance call negatives pin the shared place rule. `nested_as_ref_parameter_mutation` proves that a member reached through an `as ref` struct parameter remains C's established unchecked path; the matching Rust negative pins the documented exclusion. `captured_ref_parameter_mutation` proves a C lambda capture remains unchecked: `mutation_base_is_captured` excludes it from `mutation_is_checked_integer_ref_parameter`, preserving the established `-O0` wrap behavior. Eighteen isolated failures per target cover both spellings for add overflow, subtract underflow, multiply overflow, divide-by-zero, remainder-by-zero, constructed `MIN / -1`, constructed `MIN % -1`, postfix increment overflow, and postfix decrement underflow. Sindarin has postfix-only `++`/`--`; prefix forms are not a language feature.

This slice deliberately excludes by-value parameter mutation (including the pinned `by_value_parameter_compound_mutation` diagnostic), `int32`/`uint32`/`byte as ref`, heap-owning and instance-reference work, sync, checked capture lowering, nested/computed places, and unrelated PR-D scope. C captured scalar-ref parameters preserve their established unchecked path; Rust lambdas remain separately unsupported. Unchecked parameter behavior remains its established raw-operation policy.

## Approved strict checked-byte contract

In checked mode, source-language `byte` add, subtract, and multiply terminate nonzero when their mathematical result is outside `0..255`. Division and remainder terminate nonzero for a zero divisor. Successful boundary operations return their exact u8 result. The C runtime guards operands and range conditions before evaluating the arithmetic or returning through the byte type; the Rust lowering continues to use `checked_add`, `checked_sub`, `checked_mul`, `checked_div`, and `checked_rem`.

Unchecked/debug-overflow behavior, exact cross-target diagnostic/status parity, literal parsing, unary negation, and `SN_RUSTFLAGS` semantics remain open.

## Approved strict checked-uint32 contract

In checked mode, source-language `uint32` addition, subtraction, and multiplication terminate nonzero when their mathematical result is outside `0..UINT32_MAX`. Division and remainder terminate nonzero for a zero divisor. Successful boundary operations return their exact u32 result. The C runtime uses widened `uint64_t` intermediates for addition and multiplication, a pre-subtraction `a < b` check, and zero guards before division or remainder; Rust continues to use `u32` `checked_add`, `checked_sub`, `checked_mul`, `checked_div`, and `checked_rem`.

Unchecked/debug-overflow behavior, exact cross-target diagnostic/status parity, literal parsing, unary negation, and `SN_RUSTFLAGS` semantics remain open.

## Approved strict checked-uint contract

In checked mode, source-language `uint` addition, subtraction, and multiplication terminate nonzero when their mathematical result is outside `0..UINT64_MAX`. Division and remainder terminate nonzero for a zero divisor. Successful boundary operations return their exact u64 result. The C runtime checks operands before evaluating each operation, using `a > UINT64_MAX - b` for addition, `a < b` for subtraction, and `b != 0 && a > UINT64_MAX / b` for multiplication; division and remainder guard a zero divisor before the operation. Rust uses `u64` `checked_add`, `checked_sub`, `checked_mul`, `checked_div`, and `checked_rem`.

Coverage is **1 C codegen snapshot** proving `sn_{add,sub,mul,div,mod}_uint` helper selection; **6 C integration cases** (one successful boundary result and five isolated nonzero failure cases); and **6 Rust rgen cases** with `.expected.rs` snapshots (one successful output and five `.panic` cases). The failures on each target are add overflow, subtract underflow, multiply overflow, divide-by-zero, and remainder-by-zero. The boundary program constructs its maximum value from representable operands and checks `max-1 + 1`, `1 - 1`, `half * 2`, `max / 1`, and `max % 2` without printing values above `INT64_MAX`.

Unchecked/debug-overflow behavior, exact cross-target diagnostic/status parity, literal parsing, unary negation, and `SN_RUSTFLAGS` semantics remain open.

## Checked arithmetic optimizer semantics

At normal optimization (`-O1`/`-O2`), dead-variable elimination recursively preserves observable nested expressions and treats only checked integer `+`, `-`, `*`, `/`, and `%` initializers as potentially terminating, retaining them for both C and Rust lowering. The classifier fails closed for unknown expression kinds; calls (including static/method calls), overloaded operators, allocation, bounds-sensitive array access, dereference, and copy expressions remain preserved. The compiler explicitly supplies its checked/unchecked arithmetic mode to the shared optimizer; an unused literal remains removable, and unchecked arithmetic remains eligible for removal and native-backend semantics.

`scripts/run_tests.py` retains its `-O0` default for stable fixtures. A narrowly validated `<name>.opt` sidecar selects `default` (omit an optimization flag and use the compiler default), `-O0`, `-O1`, or `-O2` consistently for C emission/build, Rust emission/build, and C integration builds. Default-optimization regressions cover unused checked add-overflow initializers for byte, int, int32, uint32, and uint, plus divide-by-zero for uint32 and uint and `long MIN / -1` division, through C integration and Rust emit→snapshot→build→run; C snapshots prove a safe unused literal is removed and explicit `-O2` unchecked overflow is removed, with matching Rust unchecked emission coverage.

## Parity status legend

- **IBT** — implemented & behavior-tested (rgen: snapshot `.expected.rs` + `rustc` build + run + stdout diff). Because every rgen case snapshots, compiles, runs, and checks output, implemented behavior is **not** downgraded to snapshot-only when a dedicated test is missing — classify as **UT** (under-tested) instead.
- **SNAP** — Rust partial/template exists but no dedicated rgen positive test.
- **UT** — under-tested (implemented; few/no dedicated negative/edge tests).
- **REJ** — explicitly rejected with a dedicated single-line diagnostic (rgen-errors pins first line).
- **SIL** — silently unsupported: construct reaches the Rust validator and falls through to the generic "unsupported construct" message.
- **ABSENT** — C supports it; Rust has neither a template nor a validator case.

**rgen behavior:** every rgen test does emit (`--emit-rust` → `.expected.rs` snapshot) → `rustc --edition=2021` build → run binary → diff stdout vs `.expected` when one exists. A `.panic` sidecar instead marks an expected runtime failure: it requires a genuine nonzero program exit, rejects timeouts and harness launch errors, and conflicts with `.exit`; it deliberately does not match Rust panic text or an exact exit code. **There is no Rust integration suite**; the 1433 C-side behavior cases (1209 integration cases + 224 exploratory; integration includes expected runtime-failure fixtures), plus 63 + 11 C-only error tests, have **no `--target rust` equivalent**, so C-only features (files/dates/threads/closures/imports) compiled on Rust hit rejections pinned only by the 20 rgen-errors.

**Exit-code sidecar:** each rgen test may ship an optional `<name>.exit` sidecar file containing a single decimal integer that pins the expected process exit code. When the sidecar is absent, the runner defaults to expecting exit code **0**; when present, the file must hold a valid decimal integer (empty or non-numeric sidecars fail the test). A test cannot use both `.exit` and `.panic`. `main_int_exit` uses `main_int_exit.exit` (value `7`) to pin the `std::process::exit` value emitted by a zero-argument `int` main; `main_int_fallthrough` has **no** `.exit` sidecar so the runner defaults to exit **0** — its `int` main reaches the closure's unconditional `return 0` fall-through (empty stdout).

**Argument sidecar:** each rgen test may ship an optional `<name>.args` sidecar — a **JSON array of strings** that the runner passes as the process's user `argv` (run_tests.py `.args` block). An **empty array** `[]` is valid (no extra args); an **empty file** (whitespace only), **invalid JSON**, a **non-array root**, **non-string elements**, or a **string with an embedded NUL** each fail the test distinctly. The sidecar is opened as **UTF-8**. These user args are appended after `argv[0]` (the binary path), so `args.length` in the program equals `1 + len(.args)` — this is what the `main_args_*` tests assert.

**Spark 1 evidence — `test_limitation_closure_array`:** during this audit the exploratory test `test_limitation_closure_array` (a closure capturing a local array, pushed from 3 concurrent threads) produced an ASAN `heap-buffer-overflow` **twice on Spark 1**, while the same focused baseline test passed **5/5 on Spark 2** and earlier full baselines were green. Classify it as a **nondeterministic / host-sensitive existing C concurrency/closure risk** (concurrent `SnArray` push → `sn_realloc` race), **not** a docs-branch or Rust-backend regression. Keep it in the **PR-G** (threads/closures) verification scope.

| D3 | **Native pragmas/functions — sidecar C compilation vs Rust FFI** | `#pragma source`/`include` + native functions with bodies; repo rule: never emit bare `extern` forwards for native fns without bodies. | Native `.c` files must compile alongside Rust — either a **sidecar C compilation** (gcc_backend path) or direct **Rust FFI**. | **Start with Rust FFI (`extern "C"`)** for the simple case, and sidecar C compilation when a native fn has a body. Changing which files are compiled to which language is a contract change → pause for user approval. |
| D4 | **Thread panic/detach/synchronization semantics** | `src/runtime/sn_thread.h` (C runtime); C-only `expr_thread_spawn/detach/sync` (gen_model_expr.c). Rust's `std::thread` panic/detach/sync semantics differ from the C thread runtime. | Panic propagation, detach semantics, and join/barrier behavior observable to user code may diverge from C. | **Start by mirroring the C thread-runtime semantics** on `std::thread`; any semantic divergence (panic behavior, detach/join ordering) requires explicit user approval. |
| D5 | **Main argv Unicode contract — `std::env::args()` vs `args_os()`** | Normative docs define `str` as **UTF-8** (`docs/interop.md:213` "Null-terminated UTF-8 string"; `docs/strings.md:391` UTF-8 encoding). Rust `std::env::args()` yields owned UTF-8 `String` and **panics on a non-UTF-8 OS argv element**; `args_os()` + `to_string_lossy()` would silently replace invalid bytes with U+FFFD (a byte-changing lossy conversion, not parity). | A program receiving a non-UTF-8 argv element: the C backend's `strdup(argv[i])` copies the raw bytes **without** boundary/encoding validation, while Rust `std::env::args()` **enforces the declared UTF-8 invariant** by panicking. | **Use strict `std::env::args()`** (matches the normative UTF-8 `str` contract; reject lossy `args_os()`). Track **C bootstrap boundary/encoding validation** as a **diagnostic/runtime consistency risk** (C currently does not validate) — **not** an approved target exception; revisit if the C backend gains argv validation. |

# VALIDATION / MERGE GATES

Per-PR gate sequence (manual, in order):
1. **Fresh worktree:** run `make setup` **once** at the start (toolchain check).
2. **Targeted Rust tests:** run the milestone's new rgen + rgen-errors + `--target rust` integration cases.
3. **`make test-rgen`:** full Rust generation/behavioral suite green.
4. **`make build && make test`:** C default target + full suite green (C regression obligation).
5. **Independent verification on another Spark machine** (second machine re-runs build + tests to confirm reproducibility).
6. **Laptop: inspect the actual `git diff` + GitHub check runs** before merge.
7. **Docs-only caveat:** CI may **skip** docs-only PRs via `paths-ignore`, but the **manual gates above still apply** — never skip the gates because CI skipped.
8. **Merge order:** merge **serially** in milestone order (A→H); **refresh/rebase** each PR onto the updated main before merging.

# CONCLUSION / STATUS

- **Parity is NOT achieved.** The Rust backend implements a partial subset (value structs, arrays, strings, struct methods, copyOf/concat, int/long `as ref`); C-supported features across source language, runtime/SDK, diagnostics, and concurrency remain open.
- **No C-supported gap is N/A / accepted target exception.** Every missing family maps to exactly one milestone (PR-A … PR-H); each is **implementation work**, not a dismissed category.
- **Known unsupported paths require action:** each is either implemented to match C-equivalent behavior, or resolved by an **explicit user decision** (see Decision Register D1–D4). Implementation pauses only when a choice would change the language contract.
- **C remains the default target** (`src/compiler.c:31`); Rust is opt-in and every change must keep C green.
